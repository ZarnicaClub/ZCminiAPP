# ZarnicaCRM — Google Sheets → CRM
## Итоги сессии и инструкция для продолжения работы

Дата финализации: 31.08.2026

---

## 1. Задача

Добавить в будущую интеграцию ZarnicaCRM данные из Google Таблицы.

Исходная система содержит три существующих сервиса:

1. Webhook с Tilda — принимает заявки и оплаты.
2. IMAP-парсер Yandex.Почты — обрабатывает MP3/звонки.
3. CRM — собирает и отображает данные из базы.

На этапе обсуждения было принято решение **не создавать отдельный сервис на Timeweb** только ради Google Sheets. Работа с Google Sheets выполняется через Google Apps Script.

---

## 2. Какие данные нужны из Google Sheets

Источник: первый лист с рабочими данными, в частности лист `БАЛАНС`.

Интересует только строка/статья:

`Касса`

Из неё нужны:

- `Дата` — дата игры;
- `Приход` — сумма заказа;
- `№ документа` — номер БСО;
- `игроков (факт)` — фактическое количество игроков;
- `Заказчик` — имя клиента;
- `Зона отдыха` — сумма оплаты за зону отдыха;
- `order_id` — ключ связи с существующим заказом CRM.

Другие данные строки `Касса` не нужны.

Бизнес-смысл строки `Касса`: после завершения игры администратор формирует итоговый БСО и заносит его данные в таблицу.

---

## 3. Главное принятое бизнес-решение

**Строка `Касса` не передаётся, пока в ней не указан `order_id`.**

Условия передачи:

```text
Статья = Касса
И
Дата >= 13.08.2026
И
order_id заполнен
```

`order_id` — это не новый заказ. Он используется как **ключ связи с уже существующим Order в ZarnicaCRM**.

Google Sheets не создаёт новый заказ.

После нахождения существующего Order по `order_id` данные БСО должны добавляться/обновляться в этом заказе.

Если `order_id` отсутствует — строка остаётся в таблице и ждёт следующей проверки.

---

## 4. Почему не запускать отправку на каждое изменение ячейки

Обсуждался вариант запуска Apps Script при каждом изменении таблицы.

От него отказались как от основного варианта, потому что администратор может заполнять строку несколькими действиями. В таком случае можно попытаться отправить промежуточные, ещё не готовые данные.

Предпочтительная рабочая схема:

```text
Google Sheets
    ↓
Apps Script по расписанию
    ↓
проверка строк
    ↓
передача только готовых строк
```

Предварительно обсуждался запуск примерно раз в 5 минут.

Точная периодичность ещё не зафиксирована окончательно.

---

## 5. Как проверяли передачу

Чтобы не вмешиваться в существующий сервер, БД и CRM, для тестирования использовался отдельный публичный тестовый endpoint Webhook.site.

Тестовая схема:

```text
Google Sheets
    ↓
Google Apps Script
    ↓
HTTPS POST
    ↓
Webhook.site
```

Timeweb, PostgreSQL и существующий Tilda Webhook в тесте не использовались.

## 8. Результат теста №3 — финальный формат

После этого была добавлена нормализация типов.

Финальный фактически полученный JSON:

```json
{
  "order_id": 1624763921,
  "game_date": "2026-08-13",
  "order_amount": 19000,
  "bso_number": "1449",
  "players_fact": 8,
  "customer_name": "Юля",
  "rest_zone_amount": null
}
```

Этот формат подтверждён успешным получением на Webhook.site.

### Правила типов

- `order_id` → integer;
- `game_date` → `YYYY-MM-DD`;
- `order_amount` → number;
- `bso_number` → string;
- `players_fact` → integer;
- `customer_name` → string;
- `rest_zone_amount` → number или `null`.

Пример:

```text
"19 000,00" → 19000
"8" → 8
"" → null
"13.08.2026" → "2026-08-13"
```

## 11. Предлагаемая архитектура следующего этапа

После согласования соответствия полей:

```text
Google Sheets
      ↓

      ↓

      ↓
```

Важно: Google Sheets должен **дополнять существующий Order**, а не создавать новый.

---

## 12. Защита от дублей

Необходимо предусмотреть идемпотентную обработку.

Логика:

```text
order_id отсутствует
    → ничего не отправлять

order_id есть
    → отправить данные

Order с таким order_id существует
    → обновить данные

Order отсутствует
    → не создавать автоматически новый заказ
       без отдельного согласованного правила
```

Для повторных запусков Apps Script нужно будет определить механизм контроля уже синхронизированных/изменённых строк.

Предпочтительно учитывать не только факт первой отправки, но и изменение передаваемых данных, чтобы исправления администратора могли синхронизироваться повторно.
